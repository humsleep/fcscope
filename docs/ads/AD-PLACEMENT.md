> 작성 2026-10-04 · 설계 문서(코드 변경 없음) · 대상: AdMob 배너만(이 문서는 전면광고 `SearchGate` 를 다루지 않는다)
> 근거 코드: `FCScope/Core/Ads/AdsManager.swift`(`AdSlot`, `CompactAdRow`, `BannerAdView`), 각 화면 `Features/*`
> 근거 화면: `docs/review/round3/captures/`, `docs/review/round4/`

## 0. 요약

운영자 피드백은 **"광고가 너무 안 보여"** 다. 현재 상태를 진단하면 원인은 세 가지다.

1. **슬롯 위치가 모두 깊다.** 홈(`커뮤니티 최신` 위)을 빼면 첫 화면에 들어오는 슬롯이 없다. 픽 랭킹은 "공격" 순위표 10행 뒤(Max 기준 y≈900pt 이후),
   전적 "경기" 탭은 `이전 경기` 3번째 행 뒤, 리포트·선수·스타일 탭과 내 정보는 콘텐츠 **맨 끝**이다. 스쿼드 탭에는 슬롯이 아예 없다.
2. **로드 전에는 높이 0으로 접힌다**(`AdSlot(reserve: false)` 기본값). 무응답(no-fill)이면 자리가 처음부터 없었던 것처럼 보이고, 응답이 늦으면 사용자가 이미 스크롤해 지나간 뒤에 펼쳐진다.
   첫 화면 캡처(`max-dark-home.png`)에서도 홈 슬롯은 접혀 있어 보이지 않는다.
3. **SDK 시작 전(`AdsManager.starting == false`)에는 아무것도 그리지 않는다.** 이건 정상 동작(동의 거부·EEA 대응)이지만, 새 설치 기기는 동의 절차가 끝나기 전까지 배너가 없다.

이 설계는 아래 원칙으로 위 문제를 푼다.

- **메인 탭 4개(전적·스쿼드·픽 랭킹·커뮤니티)는 각각 첫 화면 또는 두 번째 화면 안에 광고 1개.** 위치는 "콘텐츠가 바뀌는 자연스러운 틈"(섹션 경계)으로 정한다.
- **모든 배너는 인라인(스크롤과 함께 움직임).** 떠 있는 탭 바 위에 고정하는 앵커 배너는 쓰지 않는다(3장).
- **첫 1.5화면 안의 슬롯은 높이를 미리 잡는다(reserve). 그보다 깊은 슬롯은 받은 뒤 편다.** (4장)
- **스크롤 1화면당 광고는 최대 1개.** 모든 광고에는 "광고" 라벨을 붙이고, 탭 가능한 요소와 **최소 24pt** 떨어뜨린다(2장).

## 1. 화면별 배치 명세

### 1-0. 공통 규격

| 항목 | 규격 |
|---|---|
| **컨테이너 A — 카드형** (`AdSlot`) | 화면 카드와 같은 가로 여백(16pt)·같은 모서리(18pt)·배경 `FC.surface2`. 위쪽 라벨 줄 `AD · 광고`(caption, `FC.muted`), 라벨 아래 6pt 뒤 배너. 카드 안쪽 여백 10pt. **본문 `Panel` 과 같은 radius 를 쓰되 배경 톤(surface2)과 라벨로 구별한다.** 테두리·그라데이션·브랜드 색은 쓰지 않는다(본문 카드처럼 보이면 안 됨). |
| **컨테이너 B — 목록 행형** (`CompactAdRow`) | 커뮤니티 목록·댓글 흐름 전용. 왼쪽 `AD` 알약 + 320×50. **위아래 여백을 지금의 5pt에서 12pt로 늘리고, 위·아래 둘 다 1pt 헤어라인을 둔다**(지금은 아래만 있다). 행과 광고의 경계가 보여야 한다. |
| **라벨 문구** | `광고` 또는 `AD · 광고`만 쓴다. Google 이 허용하는 라벨은 "Advertisements / Sponsored Links" 계열뿐이다. **"추천", "스폰서 픽", "오늘의 카드" 같은 문구 금지** — 픽 랭킹·커뮤니티의 "추천"과 헷갈린다. 화살표·"눌러 주세요"류 유도 문구도 금지. |
| **배너 크기** | 4장의 규칙을 따른다: reserve 슬롯은 **높이가 폭으로 결정되는 크기**(large anchored adaptive 크기 함수 또는 고정 320×50), 깊은 슬롯은 **inline adaptive + maxHeight**. |
| **탭 대상과의 간격** | 광고 소재(크리에이티브) 가장자리 ↔ 가장 가까운 탭 가능 영역(`.tapTarget()` 확장 영역 포함) **24pt 이상**. 컨테이너 A 는 라벨 줄 + 카드 여백(약 30pt)이 위쪽 완충이 되므로, **아래쪽에 탭 요소가 오면 바깥 여백을 추가**해 24pt 를 맞춘다. |
| **연속 제스처 영역과의 간격** | 드래그·스와이프가 계속 일어나는 영역(스쿼드 피치)과는 **75pt 이상**, 그리고 사이에 탭 불가능한 요소를 하나 이상 둔다(Google 예시의 "게임 컨트롤과 광고 간 150px" → @2x 기준 75pt). |
| **빈도** | 스크롤 1화면(기준 약 850pt — Max 956pt 에서 탭 바·내비 바를 뺀 높이)당 최대 1개. 같은 화면에 두 슬롯이 동시에 보이면 안 된다. |
| **광고 단위** | 지금은 모든 슬롯이 `AppConfig.bannerAdUnit` 하나를 공유한다. **배치별 광고 단위를 따로 만든다**(`home`, `record`, `match`, `meta`, `squad`, `community_list`, `community_detail`, `vs`, `me`). 슬롯별 노출·CTR·eCPM 을 분리해 봐야 이 문서의 가정을 검증할 수 있다. |
| **마지막 슬롯과 탭 바** | 콘텐츠 맨 끝 슬롯이 있는 화면은 `.safeAreaPadding(.bottom, 24)` 를 둔다(스쿼드·VS 는 이미 있음). 끝까지 스크롤했을 때 광고가 유리 탭 바 아래에 걸쳐 멈추면 안 된다. |

### 1-1. 전적 탭 — 홈 (`HomeView`)

**운영자 요청: `커뮤니티 최신` 섹션 제거.** `latestPosts(home.posts)` 호출만 지운다.
⚠️ 웹 저장소 `/api/v1/home` 의 `posts` 필드는 **계속 내려보낸다**(v1 계약 — 필드 삭제는 구버전 앱을 깨뜨린다). 앱이 안 그리기만 하면 된다.

**확보되는 공간**: 섹션 라벨 + 4행(행당 약 44pt) + 간격 ≈ **220pt**. 그 아래 `최근 검색`·`이런 것도 돼요` 가 그만큼 올라온다.
커뮤니티 진입은 `이런 것도 돼요` 의 커뮤니티 카드와 탭 바로 충분하다.

| 항목 | 명세 |
|---|---|
| 위치 | **`이런 것도 돼요`(featureGrid) 섹션 라벨 바로 위.** 즉 히어로 → 내 폼/예시 카드 → 즐겨찾기 → 급상승 → 지금 검색되는 구단주 → 최근 검색(있으면) → **광고** → 이런 것도 돼요. |
| 이유 | "내 것/지금 뜨는 것"(개인화·실시간 블록)이 끝나고 "기능 소개"(정적 블록)가 시작되는 경계. 광고 아래에 탭 불가능한 섹션 라벨이 오므로 아래쪽 완충이 자연히 생긴다. 위는 칩(탭 가능) → 바깥 위 여백 +8pt. |
| 형식 | 컨테이너 A + large anchored adaptive 크기(폭 결정적), **reserve = true** |
| 최대 개수 | 1 |
| 첫 화면 여부 | **Max(956pt)에서 첫 화면 안**(커뮤니티 최신 제거로 약 y 600–780pt). SE(667pt)에서는 두 번째 화면 첫머리. 내 폼 카드·즐겨찾기가 있으면 그만큼 내려가지만 두 번째 화면을 넘지 않는다. |
| 넣지 않는 경우 | 히어로 검색창에 포커스가 있고 최근 검색 드롭다운이 열린 동안에는 그대로 두되(위치가 멀다), 드롭다운 안에는 절대 넣지 않는다. |

### 1-2. 전적 결과 화면 — 탭별 (`RecordView`)

공통: 헤더(승률·스코어·폼 스트립·공유 CTA)와 `RecordTabBar` 위·사이에는 넣지 않는다. 기록 0경기 모드(빈 상태)에는 넣지 않는다(지금 규칙 유지).

| 탭 | 위치 | 형식 | 최대 개수 / 빈도 | 첫 화면 |
|---|---|---|---|---|
| **경기** | **`LastMatchCard`(마지막 경기 + 슛맵) 바로 뒤, `이전 경기` 라벨 앞.** 지금의 "이전 경기 3번째 행 뒤"보다 3행(약 200pt) 위. 위는 카드(탭 가능) → 바깥 위 여백 +12pt, 아래는 라벨(탭 불가). | 컨테이너 A, **reserve = true**(목록이 `LazyVStack` 이라 늦게 만들어지면 손가락 바로 아래에서 펼쳐진다) | 기본 1. "나머지 N경기 더 보기"를 펼치면 **이전 경기 12행째 뒤에 1개 추가**(행 ≈ 70pt × 12 ≈ 1화면). 최대 2. | 두 번째 화면 첫머리(Max y≈1050pt) |
| **리포트** | **첫 패널(`분석 리포트` 요약) 뒤, `시간대별 득실` 앞.** 맨 끝 슬롯은 없앤다. | 컨테이너 A, reserve = true | 1 | 두 번째 화면 |
| **선수** | **`내 픽 vs 인기 픽` 패널 뒤, 선수 카드 목록 앞.** 선수 카드가 15장을 넘으면 15번째 뒤 1개 추가. | 컨테이너 A, reserve = true | 최대 2 | 두 번째 화면 |
| **스타일** | **`5축 성향` 패널 뒤, `누적 슛맵` 앞.** | 컨테이너 A, reserve = true | 1 | 두 번째 화면 |

구현 메모: 지금은 `RecordView` 가 섹션 뒤에 `AdSlot()` 을 하나 붙인다. 각 섹션(`ReportSection`·`PlayersSection`·`PlaystyleSection`) 안으로 옮겨야 위 위치가 된다.
탭을 바꿀 때마다 새 배너 요청이 나가지 않도록, 탭 전환으로 슬롯이 다시 생겨도 같은 `BannerView` 를 재사용하는 방안을 구현 단계에서 검토한다(새로고침 주기 60초 이상 권고 — 출처 [G3]).

### 1-3. 매치 리포트 (`MatchReportView`)

| 항목 | 명세 |
|---|---|
| 위치 | 지금 위치 유지: **슛맵 범례 캡션("● 골 · ○ 노골…") 뒤, `팀 스탯` 앞.** 슛맵 점은 탭 가능한 인터랙티브 콘텐츠이므로 캡션(탭 불가) + 위 여백 +8pt 로 24pt 를 확보. |
| 형식 | 컨테이너 A + **inline adaptive, maxHeight 250pt**(300×250급 소재가 들어올 수 있는 자리). 체류 시간이 긴 "읽는 화면"이라 큰 소재가 어울리고 eCPM 이 높다. reserve = false(깊은 자리, 4장). |
| 최대 개수 | 1 |
| 첫 화면 | 두 번째 화면 |
| 금지 | 결과 히어로(스코어·판정) 주변, 공유 카드 버튼 주변. |

### 1-4. 픽 랭킹 (`MetaView`) — 메인 탭, 체류 긴 화면

| 항목 | 명세 |
|---|---|
| 위치 #1 | 지금 위치 유지: **첫 번째 라인 순위표(공격 10행) 패널 뒤.** 패널 경계가 자연스러운 틈이고, 순위표 행은 패널 안쪽 여백으로 이미 떨어져 있다. 바깥 위·아래 여백 +8pt. |
| 위치 #2 | **세 번째 라인 패널 뒤**(라인이 4개 이상일 때만). #1 과 약 2화면 떨어진다. |
| 형식 | 컨테이너 A. #1 은 large anchored adaptive 크기 + **reserve = true**. #2 는 inline adaptive(maxHeight 250) + reserve = false. |
| 최대 개수 | 2 (라인 수 ≥ 4) |
| 첫 화면 | #1 은 Max 에서 첫 화면 바로 아래(조금만 스크롤하면 보임), SE 에서 두 번째 화면. **"급상승 카드 뒤 · 첫 순위표 앞"으로 올리는 안은 채택하지 않는다** — 화면의 주인공(랭킹)을 광고가 밀어내고, 급상승 카드(탭)와 순위 1위 행(탭) 사이에 끼는 샌드위치가 된다. |
| 넣지 않는 경우 | 도감 검색 결과 패널(`hits`) 안·바로 아래, 로딩 스켈레톤, 오류, 빈 상태(`ContentUnavailableView`). 검색 중(`query` 2자 이상)에는 #1 을 숨기지 않아도 되지만 검색 결과와 같은 화면에 붙지 않게 결과 패널 아래 여백을 유지한다. |

### 1-5. 스쿼드 — 빌더 (`SquadBuilderView`) — 메인 탭, 체류 긴 화면

빌더 첫 화면은 피치가 거의 다 차지하고(`max-dark-squad-builder-433.png`), 피치는 **길게 눌러 끌기**가 계속 일어나는 영역이다. Google 은 "사용자가 계속 상호작용하는 화면(게임 플레이 화면 등)" 옆 배너를 명시적으로 막는다(출처 [G1][G2]).

| 항목 | 명세 |
|---|---|
| 위치 | **맨 아래 도움말 문단("슬롯을 탭해 선수를 검색·배치하고…") 뒤.** 순서를 피치 → 안내 줄 → 이름 → 저장·비우기 → (저장됨 패널) → **도움말 문단 → 광고** 로 둔다. 도움말 문단(탭 불가, 4–5줄)이 저장 버튼과 광고 사이 완충이 되고, 피치와는 75pt 이상 떨어진다. |
| 형식 | 컨테이너 A + large anchored adaptive 크기, **reserve = true**(편집 중 저장 줄 아래에서 갑자기 펼쳐지면 손가락이 걸린다) |
| 최대 개수 | 1 |
| 첫 화면 | 두 번째 화면(저장 줄을 보려고 한 번 스크롤하면 바로 들어온다). |
| 넣지 않는 곳 | 피치 위·옆·바로 아래, 칩 줄(포메이션·프리셋·내 최근 선발) 근처, **모든 시트**(포메이션·프리셋·선수 검색·사진 고르기), 알림창·확인창(비우기·불러오기). 드래그 중(`isDraggingSlot`)에는 스크롤이 막히므로 광고 위치가 바뀌지 않는다 — 그대로 둔다. |

**스쿼드 보기 (`SquadDetailView`, 공유 링크로 들어오는 읽기 전용 화면)**

| 항목 | 명세 |
|---|---|
| 위치 | 액션 줄(빌더에서 수정 · 카드 · 링크) **뒤, 바깥 위 여백 +16pt**. 읽기 전용 피치는 제스처가 없어 연속 제스처 규칙 대상이 아니다. |
| 형식 | 컨테이너 A + inline adaptive(maxHeight 250), reserve = false |
| 최대 개수 | 1 |

**스쿼드 "목록"**: 독립 화면이 없다(내 정보의 `내 스쿼드` 카드). 별도 슬롯을 만들지 않는다.

### 1-6. 커뮤니티 목록 (`CommunityView`) — 메인 탭

운영자 결정(2026-10-04): 목록 광고는 **320×50 행 모양**. 크기는 유지하고 **구별·간격만 강화**한다.

| 항목 | 명세 |
|---|---|
| 위치 | 지금 규칙 유지: 3번째 글 행 뒤(3행 미만이면 마지막 행 뒤), 이후 **15행마다**. `지금 뜨는 글`(HotBox) 안에는 넣지 않는다. |
| 형식 | 컨테이너 B(320×50), **reserve = true — 첫 슬롯만**(첫 화면 안, `LazyVStack`). 15행 반복 슬롯은 reserve = false. |
| 최대 개수 / 빈도 | 15행 ≈ 870pt ≈ 1화면에 1개. 무한 스크롤이라 상한은 두지 않되 "1화면 1개"는 빈도로 보장된다. |
| 첫 화면 | **예** (Max y≈480pt). |
| 변경점 ① | 행 위아래 여백 5pt → **12pt**, **위·아래 헤어라인**, 배너 영역 배경을 목록 배경보다 한 단계 다른 `surface2` 로(행처럼 보이되 행과 구별). 글 행은 화면 폭 전체가 버튼이라 간격이 곧 오탭 방지다. |
| 변경점 ② — **글쓰기 FAB** | 오른쪽 아래 떠 있는 `글쓰기` 버튼이 스크롤 중 광고 행 위를 지나가며 **광고를 가린다** — "콘텐츠가 광고를 가리는 것" 금지 정책(출처 [G6]) 대상. **광고 행이 FAB 영역과 겹치는 동안 FAB 를 숨긴다(페이드 아웃)**. 지금의 `fabCollapsed`(축소)만으로는 부족하다. |
| 변경점 ③ | 탭 칩(전체·인기·스쿼드·클럽-대회) 바로 아래 첫 행 위치에는 넣지 않는다(지금도 그렇다). |

## 3. 앵커 배너(탭 바 위 고정) vs 인라인 — 픽 랭킹 · 스쿼드 빌더

### 3-1. 비교

| 관점 | 앵커 적응형(탭 바 위 고정) | 인라인(콘텐츠 흐름 안) |
|---|---|---|
| **정책** | ❌ 떠 있는 유리 탭 바 바로 위 = "콘텐츠와 하단 내비게이션 사이에 끼운 배너"(Google 이 명시적으로 권장하지 않는 형태). 탭 바를 누르려다 광고를 누르기 쉽다. 위쪽 고정(내비 바 아래)도 픽 랭킹은 `.searchable` 검색창, 스쿼드는 칩 줄이 바로 붙는다. | ✅ 섹션 경계에 두고 완충을 확보하면 권장 형태. |
| **UX — 스쿼드 빌더** | ❌ 피치가 이미 Max 첫 화면을 다 쓰고 저장 줄은 탭 바에 걸친다. 앵커(약 50–60pt) + 탭 바를 빼면 SE(667pt)에서 피치를 끄는 동안 GK 슬롯이 광고 바로 위에 오고, 드래그가 광고 근처에서 끝난다 — "계속 상호작용하는 화면" 규칙과 정면충돌. | ✅ 도움말 뒤에 두면 편집 중에는 화면 밖, 저장할 때 자연스럽게 보인다. |
| **UX — 픽 랭킹** | △ 체류가 길고 스크롤 위주라 상시 노출 효과는 크지만, 순위표 행(전체 폭 버튼)이 스크롤 내내 광고 바로 위를 지나간다. 화면 높이를 상시 약 6–7% 잃는다. | ✅ 라인 패널 경계에 1–2개. |
| **유리 탭 바와의 겹침** | iOS 26 의 탭 바는 콘텐츠 위에 떠 있어 콘텐츠가 그 아래로 스크롤된다. 앵커를 그 위에 두려면 불투명 배경 + 콘텐츠 하단 inset 을 따로 관리해야 하고, 반투명 탭 바와 흰 소재가 맞붙어 "탭 바에 눌린 흰 덩어리"(이전 디자인 리뷰 지적)가 상시 남는다. `tabViewBottomAccessory` 는 내비게이션 크롬이라 광고 자리가 아니다(P4·P8). | 끝 슬롯만 바닥 여백으로 처리하면 된다. |
| **가시성(viewability)** | 매우 높음 — 항상 화면에 있다. 자동 새로고침은 **배너가 화면에 보일 때만** 돌므로, 상시 노출 자리는 세션당 노출 수가 가장 많다. | 사용자가 그 지점까지 스크롤해야 노출. 첫 1.5화면 안에 두고 높이를 예약해 손실을 줄인다. 화면 밖으로 나가면 새로고침이 멈춘다. |
| **eCPM** | 앵커 크기는 높이가 낮아(폭 기반, 최대 화면 20%) 소재 선택지가 좁고, 상시 노출 배너는 배너 무시(banner blindness)로 CTR 이 낮아지는 경향 → 노출당 단가는 낮은 편. 수익은 "노출 수"로 번다. | Google 은 스크롤 콘텐츠에 인라인 적응형이 "성능을 최대화"한다고 안내한다. 더 큰 소재(300×250급)가 들어올 수 있어 노출당 단가가 높다. 수익은 "노출당 단가"로 번다. |
| **브랜드·리뷰 리스크** | 무료 데이터 앱에서 상시 하단 배너는 10–20대 리뷰에서 "광고 덕지덕지"로 가장 먼저 지적되는 형태. 지난 UX 감사(UX-AUDIT-GENZ #1)의 "광고를 콘텐츠 뒤로" 결정과도 어긋난다. | 콘텐츠 우선 원칙 유지. |

### 3-2. 권고

**두 화면 모두 인라인.** 앵커 배너는 이번 범위에서 채택하지 않는다.

- **스쿼드 빌더**: 앵커는 정책·UX 둘 다에서 탈락(연속 드래그 화면 + 탭 바 샌드위치). 1-5 의 "도움말 뒤" 인라인 1개.
- **픽 랭킹**: 인라인 1–2개(1-4). 앵커의 노출 수 이점은 실재하지만, 떠 있는 탭 바 구조에서는 "탭 바 바로 위"가 될 수밖에 없어 오클릭 → 확인 클릭 적용·게재 제한 위험이 그 이점을 넘는다.
- **다시 검토할 조건(보류된 실험안)**: 배치별 광고 단위로 4주 측정한 뒤 픽 랭킹 #1 슬롯의 **노출/화면 진입 비율이 50% 미만**이면, 픽 랭킹에 한해 **상단 앵커(내비·검색 바 아래, 클릭 불가 12pt 경계 + "광고" 라벨)** 를 A/B 로 시험한다. 하단(탭 바 위) 앵커는 어떤 경우에도 시험하지 않는다.

## 4. 로딩 동작 — 높이 예약 vs 접기

### 4-1. 지금 상태

- `AdSlot(reserve: false)` 가 기본 — 받기 전 높이 0, 받으면 실제 높이로 펼치며 페이드. 실패하면 영구히 접힘.
- `reserve: true` 를 쓰는 곳은 없다. `CompactAdRow` 는 항상 접기.
- 결과: 화면 안에 있는 슬롯이 늦게 펼쳐지면 그 아래 콘텐츠가 90–150pt 밀린다(정책 P6 위반 소지). 반대로 너무 깊은 슬롯은 펼쳐지는 순간을 아무도 못 본다.

### 4-2. 규칙

| 조건 | 동작 |
|---|---|
| **R1. 첫 1.5화면 안 슬롯**(홈, 전적 경기 탭 #1, 리포트·선수·스타일, 픽 랭킹 #1, 스쿼드 빌더, 커뮤니티 목록 첫 슬롯) **그리고** `ads.starting && canShowAds` | **높이 예약(reserve = true).** 라벨 `광고` + 소재 크기만큼의 빈 카드(아주 옅은 `surface2`, 시머 없음 — 콘텐츠 스켈레톤처럼 보이지 않게). |
| R1 의 크기 | 예약 높이가 실제 높이와 정확히 같아야 한다 → **폭만으로 높이가 정해지는 크기만** 쓴다: 컨테이너 A 는 large anchored adaptive 크기 함수(지금 코드 그대로), 컨테이너 B 는 320×50 고정. inline adaptive 는 높이가 응답마다 달라 예약 슬롯에 쓰지 않는다. |
| **R2. 예약 슬롯의 실패·지연** | 요청 후 **6초** 안에 못 받거나 오류면 접는다. 그 슬롯이 그 순간 **화면 안에 보이면 접지 말고 그 화면을 떠날 때 접는다**(보는 중인 콘텐츠를 밀지 않는다). |
| **R3. 세션 무응답 학습** | 한 세션에서 **연속 2회** 무응답(no-fill)이면 그 세션의 나머지 예약 슬롯은 R4(접기) 모드로 바꾼다 — 빈 카드만 반복해서 보이는 것을 막는다(이전 리뷰 M7 "회색 덩어리" 회귀 방지). |
| **R4. 1.5화면보다 깊은 슬롯**(매치 리포트, 픽 랭킹 #2, 스쿼드 보기, VS, 내 정보, 커뮤니티 반복 슬롯, 상세) | **받은 뒤 편다(collapse-until-loaded).** 사용자 시야 밖에서 펼쳐지므로 보이는 콘텐츠가 밀리지 않는다. 크기는 inline adaptive + maxHeight(250 또는 컨테이너 B 는 320×50). |
| **R5. 미리 요청** | R4 슬롯도 **화면 진입 시점에 요청**한다(스크롤로 그 위치에 닿을 때가 아니라). `LazyVStack` 안의 슬롯은 근처에 와야 만들어지므로, 깊은 R4 슬롯이 `LazyVStack` 안에 있으면 R1(예약)으로 취급한다 — 늦게 만들어져 손가락 아래에서 펼쳐지는 것을 막는다. |
| **R6. 위쪽 슬롯이 뒤늦게 펼쳐지는 경우** | 사용자가 이미 슬롯 아래로 스크롤해 있는데 그 위 슬롯이 펼쳐지면 보이는 콘텐츠가 밀린다. 예약 슬롯(R1)에서는 생기지 않는다. R4 슬롯은 화면 위로 지나간 뒤에 받으면 **그 화면에서는 펼치지 않는다**(다음 진입 때 사용). |
| **R7. SDK 시작 전** | `starting == false` 면 지금처럼 아무것도 그리지 않는다(동의 거부·EEA 대응, 빈 카드 회귀 방지). |

한 줄 규칙: **"보일 자리는 정확한 크기로 미리 잡고, 안 보일 자리는 받은 뒤 편다. 보고 있는 콘텐츠는 어떤 경우에도 움직이지 않는다."**

## 5. 측정 (적용 후 2–4주)

| 지표 | 목표 / 판단 |
|---|---|
| 슬롯별 노출 ÷ 화면 진입 | 메인 탭 #1 슬롯 60% 이상. 50% 미만이면 위치를 한 섹션 위로 검토(픽 랭킹은 3-2 실험안). |
| 슬롯별 CTR | 다른 슬롯 평균의 2배를 넘는 슬롯 = 오클릭 의심 → 간격 재검토. |
| 슬롯별 eCPM · 일 수익 | 인라인 큰 소재 자리(매치·VS·픽 랭킹 #2)의 단가가 높게 나오는지 확인. |
| 일치율(match rate) · 표시율 | 낮으면 위치가 아니라 수요 문제 — 예약 슬롯 R3 동작이 자주 걸리는지 함께 본다. |
| 리텐션 · 앱스토어 리뷰 | "광고 많다" 언급이 늘면 픽 랭킹 #2·전적 경기 탭 #2 부터 뺀다. |
